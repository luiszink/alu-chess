Container-Reduktion

Ein kombinierter Scala-Kafka-Worker

Vorher gedacht

  • AI-Worker als Container
  • Persistence-Worker als weiterer Container
  • Stockfish-Worker separat

Implementiert

  • kafka-scala-worker startet zwei Scala-Consumer
  • stockfishworker bleibt separat wegen Python + Stockfish
  • Nur ein Kafka-Broker: kafka
Das Routing bleibt sauber, weil AI und Persistenz unterschiedliche Topics und Consumer Groups nutzen.
Deployment Weniger Container, gleiche fachliche Trennung

Demo-Ablauf

So kann die Implementierung gezeigt werden

Start

docker compose up --build

Startet Kafka, MongoDB, Controller, Model, Scala-Worker und Stockfish-Worker.

Beobachten

docker compose logs -f kafka-scala-worker

Zeigt AI-Consumer und Persistence-Consumer im selben Scala-Worker.

Fachlicher Test

Partie beenden oder importieren.

Der Controller publiziert ein Persistenz-Event; der Worker schreibt nach MongoDB.

Cleanup

docker compose down --remove-orphans

Hilft nach Service-Umbenennungen oder Profil-Starts.

Fazit

Was verbessert die Kafka-Architektur?

  • Controller und Model sind weniger direkt an Worker-Implementierungen gekoppelt.
  • KI, Engine und Persistenz laufen ueber klare Topic-Schnittstellen.
  • Kafka wird aktiv genutzt: Consumer berechnen, fragen Engine an und schreiben Datenbank.
  • Der Scala-Worker reduziert Container-Anzahl, ohne fachliche Verantwortungen zu vermischen.
  • MongoDB ist Standard; Postgres bleibt ueber vorhandene DAOs moeglich.
Kurzform fuer die Vorstellung: Ein Kafka-Broker, drei fachliche Integrationen, klare Topics, aktive Consumer.
